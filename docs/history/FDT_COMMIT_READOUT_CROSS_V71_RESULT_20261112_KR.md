# V71 저장 의미 상태·언어 출력기 교차 진단 — 2026-11-12

**오류 유형별로 발생 지점이 달랐다.** V70에서 새로 생긴 시각 구분자와 Cyril 이름 오류는 마지막 언어 readout을 바꾸는 것만으로 재현됐다. `27→2&`는 새 Commit·결합 쪽으로 바꾸면 두 readout에서 모두 재현됐다. Inez와 장문17→16은 양쪽을 함께 바꾼 조건에서만 해당 오답이 나왔다.

이 결과는 ‘의미 상태가 모두 잘못됐다’ 또는 ‘출력기만 고치면 된다’는 한 가지 결론으로 축약하기 어렵다는 근거다. 현재의 의미 디노이징은0회이며, 다음은 언어 추출·메모리 결합과 언어화 경계를 나눠 안정화하는 작업이다.

## 실제 측정

이미 끝난 V67/V70의 같은 입력에서 저장된 bound Commit을 사용했다. 문장 인코더를 다시 돌리지 않고 실제 전체 크기의 old/new 마지막 언어 readout에 각각 넣어 **CPU 모델 호출4회,선정 사례8개**를 측정했다. 출력기 입력은 기존 메모리값 local512차원+global2×512차원과 원래 terminal flag뿐이다. 골드 문자·위치·원문은 사후 채점에만 사용했다.

현재 role_projection은 코드상 OrderedFuzzyReadout 안에 있지만, 실제 실행에서는 Commit을 만들 때 적용된다. 이번 교차 진단의 ‘새 상태’에는 이 **추출·결합 쪽 변화도 포함**되고, ‘마지막 readout’은 그 후의7개 parameter tensor를 뜻한다. 이 경계를 흐리면 원인 해석이 달라진다.

표는 선택한 문자의 argmax다. 완성 문장 전체를 새로 생성해 평가한 점수나 무작위 사례의 정확도가 아니다.

| 선정 사례의 원문 문자 | 원상태+원readout | 원상태+새readout | 새상태+원readout | 새상태+새readout |
|---|---|---|---|---|
| 6:45의 `:` | : | 0 | : | 0 |
| 27의 마지막 `7` | 7 | 7 | & | & |
| Inez의 `z` | z | z | z | 9 |
| U-24의 `U` | 1 | 1 | U | U |
| 장문17의 마지막 `7` | 7 | 7 | 7 | 6 |
| 장문28의 마지막 `8` | 4 | 8 | 4 | 8 |
| Cyril의 `C` | C | b | C | b |
| 보존 대조 문장의 `N` | N | N | N | N |

- 시각 `:`와 Cyril은 새 마지막 readout만으로 오답이 나왔다. 원 readout은 새 Commit에서도 원문 문자를 읽었다. 이 두 위치의 재현에 필요한 정보가 새 Commit에서 읽힐 수 있다는 뜻이며, 모든 추상 의미 형성이 완료됐다는 뜻은 아니다.
- `27`의 경우 새 Commit을 원 readout에 넣어도 `&`를 골랐다. 이는 추출·결합 쪽 변화가 이 관측 오답을 재현할 수 있음을 뜻한다. 정보가 영구 소실됐다거나 어느 인코더 층·퍼지 앵커 하나가 유일 원인이라고 확정하지 않는다.
- Inez·17에서는 각각 한쪽만 바꾸면 정답 문자를 유지했다. 두 변경을 합친 상태에서 결정 경계를 넘는 결합 문제가 관측됐다. 예를 들어17의 정답 margin은 원조합+2.111,readout만 변경+0.438,상태만 변경+0.135,양쪽 변경−1.421이었다.
- 교정 사례도 양쪽에서 나왔다. U-24는 새 Commit 쪽으로 바꿀 때 교정됐고,28은 새 마지막 readout 쪽으로 바꿀 때 교정됐다. 따라서 유용한 양쪽 가중치를 모두 보존했다.

## 신뢰 범위와 한계

CPU FP32와 원래 native BF16/FP32 차이를 먼저 검사했다. 두 원래 조합의8초점 문자와 **256개 patch 위치 argmax가 모두 원래 저장 결과와 같았다.** 원래 BF16 경로의 logits에는 약0.0015–0.0018 상대 L2 차이가 있었고 원래 FP32 장문은 약4e-7 수준이었다. 선택한 판정은 정밀도 차이로 뒤집히지 않았다.

모든 교차 조합이 실제 훈련 때의 상태 분포라고 보장되지는 않는다. 개선·퇴행을 본 뒤 고른8개 사례이므로 위 패턴의 개수를 모델 전체 오류 비율이나 보편적 인과 분해로 삼지 않는다. [ICLR의 activation patching 방법 검토](https://proceedings.iclr.cc/paper_files/paper/2024/hash/06a52a54c8ee03cd86771136bc91eb1f-Abstract-Conference.html)와 [해석 지침](https://arxiv.org/abs/2404.15255)도 측정 방법·개입 분포에 따른 해석 범위를 점검할 참고 자료로 읽었다. 해당 논문이 현재 FDT의 원인을 증명하는 것은 아니다.

## 바로 준비한 후속

V72는 **추출·결합 가중치를 고정하고 마지막 언어 readout7개 tensor만 학습하는 첫 단계**로 준비했다. 입력마다 K_P/K_C를 실제로 읽어 다른 Commit을 만드는 구조와 세 은행 경계는 유지한다. 이름·연속 숫자만 강조하던 TRAIN loss를 시각·소수·부호·통화·단위 등 완전한 수치 표현으로 확장하고, 이미 맞힌 비중요 TRAIN 위치에는 초기 readout의 확률을 유지하는 작은 Bernoulli KL을 제안했다. 교사 정답 여부 필터는 TRAIN loss에만 적용하며 평가 행을 거르지 않는다.

CPU 자료는 기존 V70 TRAIN512행을 그대로 보존하고 새 표현128행을 추가한640행/954,100 UTF-8바이트다. 새 DEV32행을 분리했다. 모든672행의 source span,43,992 중요 바이트,16개 위치 역할,단일 유한 순서,held 이름의 TRAIN 부재를 독립 확인했다. 실제 NN 입력 feature는 id/prompt뿐이며 새 정답 구간은 별도 파일이다. 정답·regex 결과를 추론 입력으로 쓰지 않는다.

숫자 전체 표현 fixture,KL 정지점/복구 방향 기울기·중요/PAD/교사오답 위치의 anchor 제외,작은 실제 모듈에서 upstream+role_projection 동결/마지막7개 tensor만 gradient가 흐르는 계약을 확인했다. **이는 CPU 자료·loss 후보이며 실제 V72 runner·cache/cursor/Adam/scaler/모든 RNG의 전체 복구·OS preflight·실행 계획·봉인·GPU는 아직 없다.** 작은 fixture 3회 forward를 새 모델 능력이나 실제 학습 개선으로 세지 않는다.

다음에는 이 경계에 맞는 실제 driver와 고정 비용·저장·복구 계약을 완성해 한 번의 제한 학습을 진행한다. 이후 원문 의미의 가용성 문제가 남으면 언어 readout을 고정한 추출 쪽 학습을 따로 판단한다. 현재 언어 사이클의 개선 중이며 디퓨전으로 넘어가지 않았다.
